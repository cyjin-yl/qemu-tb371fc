# SM8250 global clock controller

`qcom-sm8250-gcc` is a register-level, digital clock and reset model. It exposes
real SM8250 offsets and binding indices, computes rates from programmed clock
sources and dividers, and changes its outputs when clocks, votes, resets or
software-controlled power domains change. It is not a complete SM8250 clock,
voltage, firmware or electrical model.

The TB371FC machine maps it at **0x00100000**, with a **0x001f0000** aperture and
a stable QOM child `/machine/gcc`. Unknown addresses return `MEMTX_ERROR` and
produce `LOG_UNIMP` diagnostics; there is no catch-all register RAM that makes
unimplemented hardware appear to work. Enable diagnostics with
`-d unimp,guest_errors`.

## Actual tablet observations and frequency assumptions

The [new device inventory](../evidence/expansion-20261123/android-device-inventory.json)
and [sysfs/kernel metadata](../evidence/expansion-20261123/android-sysfs-hardware.json)
record the following read-only observations:

- GCC is `/soc/qcom,gcc@100000`, compatible `qcom,gcc-kona` and `syscon`, with
  region `[0x100000, 0x1f0000]` and one clock/reset argument. Its DT node has
  no `clocks` or `clock-names` property.
- `xo_board` is a fixed **38,400,000 Hz** DT clock. Combining that fact with
  the cited Kona RPMh divider gives **19,200,000 Hz bi_tcxo** as a source-based
  inference. It is not a runtime GCC register or `clk_summary` measurement.
- `chip_sleep_clk` is a fixed **32,000 Hz** DT clock. The machine therefore
  supplies 32 kHz, not an assumed 32.768 kHz.
- The production kernel has `CONFIG_DEBUG_FS` disabled and no debugfs mount.
  No runtime clock summary was available, and no clock registers were written.
- GCC's real voltage supplies reference RPMh CX/CX_AO/MMCX regulators. This
  model does not implement those voltage votes or infer safe physical voltage
  from a successful digital clock transition.

The machine exposes a configurable `bootstrap-fabric-hz` value, currently
**100 MHz**, solely to supply wrapper 2's M/S AHB parent inputs for the direct
Linux entry configuration. That number is a declared bootstrap assumption; it
was not measured on the tablet. Other unknown external branch parents remain
unconnected and their branches remain stopped even if software sets enable.

## Digital state transitions

### PLLs and source rates

GPLL0, GPLL4 and GPLL9 use bases `0x00000`, `0x76000`, and `0x1c000`. HLOS votes
are independent bits **0, 4, 9** of register `0x52018`. A requested PLL with a
valid XO input and in-range L/alpha configuration locks after a synthetic
5 microsecond virtual delay. No vote, a manual standby/reset, an offline
request, or a missing XO removes lock and stops output.

The model also supports the manual OPMODE/RESET_N/OUTCTRL sequence used by the
Lucid driver. L and the 16-bit alpha value produce
`xo * (L + alpha / 65536)`. While running, changes remain shadow programming
until an UPDATE latch completes. The latch acknowledgement follows a separate
synthetic 1 microsecond transition and can occur with the output disabled, as
required by the upstream programming path. Invalid configuration does not
produce a success acknowledgement. The known aggregate USER_CTL output
settings 0 and 7 are supported; independently gated partial output combinations
are diagnosed as unsupported rather than assigned guessed wiring.

No analog tuning, lock noise, voltage-dependent instability or calibrated lock
time is simulated. CONFIG_CTL/TEST_CTL tuning registers have an explicit zero
model default; nonzero writes are rejected with diagnostics. GPLL4/GPLL9 have
no invented startup frequency and must be programmed by a firmware/platform
model or the guest.

### RCGs and branch votes

An RCG has separate shadow and active CFG/M/N/D values. Writing CMD.UPDATE
starts a synthetic 1 microsecond commit if the parent selector and M/N/D
encoding are valid. Invalid programming leaves UPDATE pending, retains the
previous active configuration and logs the failure. Programming a stopped PLL
parent can commit valid divider state; it does not make that parent run or clear
the root's actual stopped status.

Rates use the Linux half-divider convention: nonzero HID field `h` divides by
`(h + 1) / 2`. In dual-edge M/N mode, `n = (~N & mask) + M`; D is retained and
validated as the duty-cycle counter encoding. The model propagates the
resulting frequency, but does not emit individual clock edges or simulate the
duty-cycle waveform. DFS is explicitly disabled; an attempt to enable DFS is
rejected and logged.

A branch is active only when requested and when its parent produces a clock.
HLOS bits remain independent when multiple branches share a vote register.
`remote-vote[N]` inputs allow another model to hold a documented PLL/branch
request after the HLOS vote is cleared. For branches with HWCG enabled,
`hw-request[N]` supplies the consumer request. These inputs are indexed by the
clock binding. The default is no remote vote and no hardware request; absent
remote processors are not silently treated as permanent voters.

Parent relationships absent from the Linux descriptor are exposed as explicit
`<clock-name>_parent` Clock inputs. This includes fabric and PHY/symbol clocks.
The model does not guess that all such clocks share one oscillator. A branch
request with a missing external parent leaves CLK_OFF asserted and outputs
zero Hz.

### Reset and power

The `reset` GPIO array uses all 45 binding indices. A BCR changes its peripheral
reset output; it does not erase unrelated GCC programming. Video AXI reset
bits share their CBCRs, so asserting bit 2 preserves clock-enable bit 0.

The `power` GPIO array uses the 11 upstream GDSC indices. A software collapse
request changes the PWR_ON readback/output after a synthetic 3 microsecond
transition. Autonomous HW_CONTROL is rejected because its physical controller
and conditions are absent. Memory retention, regulator supply state, isolation,
remote power voters and power-dependent analog behavior are not implemented.
Peripheral power behavior exists only where the machine connects and the
receiving device consumes the output; an exposed GDSC status alone does not
establish that an entire peripheral or NoC is modeled.

## Cold state and firmware handoff are separate configurations

The device property `boot-configured` defaults to **false**. This cold model
state uses zero PLL programming, no HLOS clock votes, inactive resets, collapsed
software power domains, and initial RCG XO selections without requests. These
are explicit model defaults, **not captured silicon power-on values**.

The TB371FC machine's `gcc-boot-configured` property defaults to **true** for
its declared direct-Linux firmware handoff. This initializes GPLL0 to 600 MHz,
its documented even divider to 300 MHz, and wrapper 2 SE4 to 7.3728 MHz with
M=384, N=15625 and HID=1. It enables the UART, M_AHB and S_AHB HLOS votes.
This is derived from the driver's clock table and the existing console setup;
it is not a copy of a captured stock bootloader register image.

The machine connects the UART to the actual GCC outputs
`gcc_qupv3_wrap2_s4_clk`, `gcc_qupv3_wrap_2_m_ahb_clk`, and
`gcc_qupv3_wrap_2_s_ahb_clk`, and reset output 26 to the GENI reset input.
[GENI clock/reset behavior](geni-uart.md#clock-and-reset-inputs) explains what
those connections do. Other downstream device connections must be assessed
individually.

## Migration and verification

VMState retains programming, active divider/PLL state, votes, power state and
pending transition deadlines. Incoming state is validated and output clocks and
GPIOs are recomputed. This is a migration implementation, not a test result by
itself. The dedicated test transfers a running clock with a pending divider
commit, pending power transition, remote vote, asserted reset and RAM marker
between two real QEMU processes, then checks continuation. QTest owns each
process's virtual time, so the migration harness explicitly aligns that test
clock before transfer; the checked deadlines are not physical timing evidence.

Run the compiled model in the development container:

```sh
python3 tb371fc/tests/test_gcc_sm8250.py --qemu /work/build-next/qemu-system-aarch64 --work-dir /work/gcc-qtest
python3 tb371fc/tests/test_gcc_sm8250.py --qemu /work/build-next/qemu-system-aarch64 --migration-only --work-dir /work/gcc-migration
python3 tb371fc/tests/test_geni_clock_reset.py --qemu /work/build-next/qemu-system-aarch64 --work-dir /work/geni-clock-qtest
python3 tb371fc/tests/test_geni_clock_reset.py --qemu /work/build-next/qemu-system-aarch64 --migration-only --work-dir /work/geni-clock-migration
```

The GCC test explicitly selects `tb371fc,gcc-boot-configured=off,ufs-enabled=off`; the linked
GENI test selects `tb371fc,ufs-enabled=off` with firmware handoff. UFS is
excluded from these component/migration tests because its controller core does
not yet support in-flight migration; this is not whole-board migration support. Tests use real MMIO, QOM Clock
period observations, GPIO interception and serial bytes, with bounded socket
and process waits. QTest's raw `readl`/`writel` protocol does not return
`MemTxResult`, so unsupported-access checks verify diagnostics and lack of
state mutation; they do not claim to prove a CPU-visible synchronous abort.
JSON output records the binary SHA-256 and passes/failures, and intermediate
logs remain in the chosen directory. Python optimization is rejected so it
cannot silently disable assertions.

These receipts were collected before UFS was added to the default machine.
They establish the tested component configuration, not migration of the later
expanded board. Current scripts explicitly select `ufs-enabled=off`; the
recorded binary predates that property, so reproducing these historical tests
with that binary requires `--machine tb371fc` (or, for cold GCC,
`--machine tb371fc,gcc-boot-configured=off`). Do not replace the recorded binary
identity with a later build identity.

A first startup attempt uncovered a genuine QOM initialization bug in the
machine: it cast the embedded GCC object to DeviceState before initializing
the child. A core backtrace identified that site, and the cast was moved after
initialization. The first GCC timer test also exposed a harness error: `-S`
disables virtual timer dispatch even though QTest can advance its virtual clock.
The corrected harness enables the QTest VM event loop, explicitly pauses for
migration and resumes to verify timer-driven continuation. It uses the time
returned by a positive clock step; QEMU 11 rejects `clock_step 0`. Device
acknowledgements were not made unconditional to accommodate either issue.
